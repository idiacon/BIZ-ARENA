# Biz Arena: аудит структуры и UX

Дата: 2026-07-01

## Целевая логика продукта

Biz Arena должна вести пользователя по состоянию матча, а не показывать все возможности одновременно.

### Преподаватель

1. `/server`: состояние сервера, сеть, ссылка и создание комнаты.
2. Создание комнаты: сценарий, длительность, вместимость и правила.
3. Лобби: ссылка/QR, список учеников, готовность и проверка настроек.
4. Матч: кабинет преподавателя, управление ходом, готовность класса, помощь застрявшим командам и Crisis Cards.
5. Разбор: результаты, события, динамика рынка и экспорт отчета.

### Ученик

1. `/client` или публичная ссылка: код комнаты, имя и компания.
2. Лобби: параметры матча, участники и одно действие `Готов`.
3. Матч: маршрут `Купить -> Нанять -> Собрать -> Продать -> Завершить ход`.
4. Результаты: место, прибыль, объяснение результата и следующий учебный вывод.

## Исправлено в этом проходе

- Локальный host `/server` стал преподавательской консолью, а не дополнительной компанией-конкурентом.
- Действия преподавателя из локального приложения направляются в localhost-only `/api/server/action`.
- На мобильном экране управление матчем поднято выше длинной аналитики.
- Следующее действие преподавателя открывает кабинет преподавателя, а не экономическую вкладку фиктивной компании host.
- Готовность преподавательской панели различает готовность к старту и готовность к текущему ходу.
- Ученическое лобби отделяет принятие участия от полного маршрута первого хода.
- Боковые показатели рынка строятся из реального состояния комнаты; статические демонстрационные показатели удалены.
- С главного меню удален фиктивный активный матч с выдуманными командами и балансами.
- Из выбора режима удалены неработающие вкладки `Мои комнаты` и `История матчей`.

## Текущие структурные риски

### P1: фронтенд слишком концентрирован

- `public/app.js` остается общим контроллером нескольких ролей.
- `public/styles.css` содержит большой исторический слой правил.
- Следующий безопасный разрез: screen routing, transport/session, shared render helpers и role-specific UI.
- Перед каждым разрезом нужны регрессионные тесты текущего поведения.

### P1: создание комнаты нужно сделать первым рабочим объектом экрана

Форма параметров должна идти перед длинными объяснениями. Преподавателю важнее создать комнату, затем проверить правила и сеть.

### P1: экран результатов перегружен

Первый уровень должен отвечать на три вопроса: кто победил, почему, что обсудить. Подробные таблицы и replay рынка должны быть вторым уровнем.

### P1: устаревшие корневые копии

Корневые `index.html` и `translations.js` не являются обслуживаемым приложением. Канонический frontend находится в `public/`. Копии нужно удалить после проверки release scripts и Electron entry points.

### P2: производительность

- Завершить переход от полного рендера комнаты к подписям изменившихся панелей.
- Вынести настоящий thin student summary, а не фильтровать большой общий объект.
- Измерить long tasks, число DOM updates и память на слабом ноутбуке.

## Что берем у аналогов

- OpenRCT2: четкое разделение сценария, sandbox и multiplayer; дисциплина совместимости сохранений и релизов.
- Canvas LMS: преподавательские роли, права, журнал действий и обзор класса.
- Hedy: пошаговое обучение, прогресс учеников и учительский мониторинг затруднений.
- boardgame.io: явная модель фаз/ходов, lobby и журнал событий; использовать как архитектурный ориентир без миграции текущего runtime.
- Mesa: идеи моделирования экономики и экспериментов; не добавлять Python runtime в клиент.

Код и ассеты GPL/AGPL-проектов не копировать без отдельной лицензионной проверки. Использовать их как источник продуктовых и архитектурных паттернов.

## Инструменты

- GitHub CLI установлен. Для операций от имени пользователя требуется один интерактивный вход: `gh auth login`.
- Ollama доступна как локальный API и подходит для автоматизированного второго мнения.
- Qwen Desktop установлен как отдельный GUI. Пока он не является вызываемым из scripts/CI агентом.
- OMX исправен для параллельных независимых задач; не применять его к каждой мелкой правке.

Наиболее полезные установленные навыки: `ui-ux-pro-max`, `game-ui-frontend`, `frontend-testing-debugging`, `data-visualization`, `code-review`, `security-scan` и `threat-model`.

## Следующий проход

1. Перестроить экран создания комнаты вокруг формы и короткого preflight.
2. Упростить результаты до summary -> причины -> подробности.
3. Проверить и удалить устаревшие корневые frontend-копии.
4. Начать разрез `public/app.js` с transport/session слоя, сохранив API и role contracts.
5. Повторить desktop/tablet/mobile screenshot QA и classroom/cloud smoke.

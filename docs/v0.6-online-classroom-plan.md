# Biz Arena Online Classroom v0.6

## Цель

Превратить Biz Arena из локального classroom-прототипа v0.5 в онлайн бизнес-симулятор для вуза:

- преподаватель ведет занятие через серверный режим;
- студенты подключаются через `BizArena Client.exe` или браузерный fallback;
- игровая логика, комнаты, действия и хранение остаются на сервере;
- Local Classroom остается рабочим сценарием для аудиторий без интернета;
- Cloud Classroom готовится под Oracle Free VM как основной durable-путь.

## Выбранные решения

- Основной фокус v0.6: онлайн-класс, но без поломки Local Classroom.
- Хостинг: Oracle Free VM для устойчивого бесплатного режима, Render только для demo/fallback.
- Клиент: `BizArena Client.exe` как основной вход студента, браузер как резервный вариант.
- Хранение: SQLite как целевой backend для cloud/server mode; JSON остается migration/backup fallback.
- Стек: Node.js, Electron и vanilla JS остаются. React/Next/Unity/C++ не вводим.
- Старый internet tunnel остается legacy/unsupported и не является classroom-планом.

## Skill routing

Новые skills используем не как самоцель, а как рабочие дорожки v0.6:

| Зона | Skills | Как применяем |
| --- | --- | --- |
| Планирование и карта проекта | `writing-plans`, `graphify`, `analyze`, `improve-codebase-architecture` | Держим roadmap в `docs/`, строим implementation-plan перед кодом, используем граф/поиск для поиска связей вместо угадывания. |
| Server/Admin/Client split | `frontend-skill`, `ui-ux-pro-max`, `web-game-foundations`, `game-ui-frontend` | Разделяем преподавательский cockpit, клиент ученика и игровые панели без смены стека и без маркетинговых экранов. |
| Electron и classroom build | `electron`, `agent-browser` | Проверяем Server.exe/Client.exe, desktop-mode, URL routing, packaged smoke. |
| Performance и Thin Client | `browser-trace`, `agent-browser`, `verification-before-completion` | Измеряем DOM/network/console, оставляем polling fallback, доказываем, что unchanged state не вызывает тяжелый rerender. |
| Security | `security-scan`, `threat-model`, `code-review` | Проверяем teacher sessions, player sessionToken, localhost-only server actions, ownership rooms. |
| Render demo | `render-deploy` | Используем только для demo/fallback cloud URL; durable classroom ведем через Oracle/диск. |
| Документы и защита | `documents`, `humanizer` | Обновляем teacher handoff, defense brief, demo script и fallback plan человеческим языком. |

Отдельно: подходящего SQLite/Electron storage skill в локальном списке не найдено. Поэтому перед полноценным SQLite adapter нужен отдельный spike: проверить `better-sqlite3` или альтернативу на Electron 30 + electron-builder, native rebuild, packaged Server/Client exe. GitHub-issues по `better-sqlite3` и `electron-rebuild/sqlite3` показывают, что ABI/rebuild packaging может ломаться, поэтому SQLite не внедряем вслепую.

## Порядок работ

### 1. Архитектурная карта и контроль плана

Результат:

- `docs/architecture-map.md` с картой подсистем;
- список зон, которые надо отделить перед большим рефактором;
- этот документ как рабочий roadmap v0.6.

Проверяем:

- server core;
- storage;
- API;
- teacher/admin UI;
- student/client UI;
- Electron shell;
- release/package scripts;
- старые документы с mojibake или legacy-решениями.

### 2. Разделение Server/Admin/Client

Цель: `BizArena Server` становится панелью преподавателя, а не игрой хоста.

Сделать:

- `/server` и desktop server mode показывают управление занятием;
- `/client` и desktop client mode показывают вход студента и игру;
- teacher/admin actions остаются отдельно от player actions;
- игровые панели, нужные только студенту, не перегружают admin mode.

Acceptance:

- преподаватель создает комнату, видит участников, готовность, блокеры и управляет ходами;
- студент видит только вход, лобби, свой первый ход и результаты;
- cloud teacher endpoints работают только по teacher session;
- local server admin action остается localhost-only.

### 3. Thin Client v2

Цель: студентский клиент получает минимальный student summary, а не большой `roomSummary`, отфильтрованный после сборки.

Сделать:

- выделить отдельный read model для student view;
- оставить teacher/full summaries для админки и тестов;
- уменьшить DOM-перерисовки на `/client`;
- сохранить WebSocket как push invalidation, а HTTP как fallback.

Acceptance:

- `/api/state?view=student` не содержит лишнюю внутреннюю модель других команд;
- unchanged-state не вызывает полный rerender;
- lite mode остается `data-performance-mode="lite"`;
- smoke:cloud проверяет thin state.

### 4. SQLite persistence

Цель: подготовить durable cloud/server mode без зависимости от JSON-файла как основного backend.

Сделать:

- добавить `BIZ_ARENA_STORAGE=sqlite|json`;
- добавить optional `BIZ_ARENA_SQLITE_PATH`;
- сделать storage adapter interface:
  - `loadDb()`;
  - `saveRoomSnapshot(room)`;
  - `loadActiveRooms()`;
  - `saveTeacher(account)`;
  - `saveTeacherSession(session)`;
  - `appendActionAudit(entry)`;
- использовать `better-sqlite3` как основной кандидат для Electron packaging;
- добавить migration script: `biz-arena-db.json` -> `biz-arena.sqlite`;
- не удалять JSON автоматически.

Минимальные таблицы:

- `teachers`;
- `teacher_sessions`;
- `rooms`;
- `room_snapshots`;
- `action_audit`;
- `schema_migrations`.

Acceptance:

- JSON backend продолжает работать;
- SQLite backend стартует с `BIZ_ARENA_STORAGE=sqlite`;
- active rooms и teacher sessions восстанавливаются после restart;
- corrupted JSON recovery остается покрыт тестами;
- Oracle profile явно падает с понятной ошибкой, если SQLite недоступен.

### 5. Oracle Free VM deployment profile

Цель: подготовить production-ready инструкцию и конфигурацию для durable cloud classroom.

Сделать:

- production env profile:
  - `NODE_ENV=production`;
  - `BIZ_ARENA_DEPLOYMENT=cloud`;
  - `BIZ_ARENA_APP_MODE=server`;
  - `BIZ_ARENA_STORAGE=sqlite`;
  - `BIZ_ARENA_DATA_DIR=/var/lib/bizarena`;
  - `BIZ_ARENA_PUBLIC_URL=https://...`;
  - `BIZ_ARENA_ALLOW_REGISTRATION=false` после первого teacher setup;
- systemd unit;
- nginx reverse proxy пример;
- firewall checklist;
- `/api/health` и readiness-check.

Acceptance:

- cloud runbook описывает first setup и закрытие регистрации;
- WebSocket proxy работает через nginx;
- Local Classroom fallback остается в инструкции.

### 6. Teacher UX

Цель: преподаватель за 10 секунд видит состояние класса.

Сделать:

- отдельный dashboard преподавателя:
  - карточки класса;
  - список комнат;
  - выбранная комната;
  - таблица команд;
  - фильтры по капиталу, прибыли, выручке, продажам, складу, долгу;
  - блок "Кому нужна помощь";
- timeline занятия: лобби -> ход -> расчет -> разбор -> финал;
- убрать лишние игровые панели из admin mode.

Acceptance:

- видны connected/ready/stuck/no purchase/no workers/no assembly/no sale/bankruptcy risk;
- доступны pause/resume/next turn/finish;
- есть блок "Что сделать преподавателю сейчас".

### 7. Student First Turn

Цель: первый ход ведет игрока по маршруту без длинной инструкции преподавателя.

Маршрут:

1. Закупка.
2. Персонал.
3. Сборка.
4. Маркетинг.
5. Завершить ход.

Сделать:

- блок "Что делать сейчас";
- одну главную next-action кнопку;
- status каждого шага: не начато, готово, требует внимания;
- короткий советник: проблема -> причина -> действие;
- разбор после первого расчета: прибыль, продажи, почему товар продался или не продался.

### 8. Экономика и Simformer parity

Сделать:

- усилить закупки: поставщики, дефицит, разные цены, исчезновение лотов после покупки другим игроком;
- улучшить ботов: конкурируют за дешевые компоненты, выставляют разумные цены, реагируют на спрос;
- улучшить маркетинг: лучшая цена, моя цена, рекомендованная цена, ожидаемые продажи, риск не продать;
- обновить `docs/simformer-parity-matrix.md`.

### 9. Security pass

Сделать:

- клиент не управляет чужим игроком через `playerId`;
- все player actions проверяют session token;
- teacher actions проверяют teacher session и ownership комнаты;
- добавить/расширить action audit log;
- проверить HTML escaping, export JSON, room codes, teacher registration;
- после первого teacher setup закрывать регистрацию.

### 10. QA, release и дипломные материалы


Для release pass:

```powershell

```

Материалы:

- руководство преподавателя;

- сравнение с Симформером;
- отчет по тестированию.

## Ближайший implementation slice

После архитектурной карты начинать с разделения Server/Admin/Client и Thin Client v2, а SQLite делать следующим крупным этапом. Причина: если сначала внедрить SQLite, текущие смешанные роли server/client/admin закрепятся глубже в storage и API.
